# Spike 2026-10-22: accuracy, token cost, scanner implementation

Two Claude Fable 5.1 agents ran this spike in parallel:

- [`2026-10-22-research.md`](2026-10-22-research.md): Claude Code and Claude-model mechanics,
  sourced from the official docs and the `claude-api` skill.
- [`2026-10-22-empirical.md`](2026-10-22-empirical.md): two throwaway entry-point scanners
  (Python regex vs JavaParser AST, plus a javac parse-only test) measured on four real
  repositories (spring-petclinic-rest, jhipster-sample-app, nacos 3k files, thingsboard 5.5k
  files) and a synthetic fixture of hard cases.

The fixture and the javac prototype are kept in [`2026-10-22-prototypes/`](2026-10-22-prototypes/).
The other prototype paths in the empirical report pointed to a temporary directory that no
longer exists.

The reports disagreed on one point, the Java parser. The measurements settled it (see 1).

## Recommendations

### 1. Scanner: Java on the javac Tree API, not JavaParser

| | javac Tree API (`jdk.compiler`) | JavaParser 3.27 | Python regex |
|---|---|---|---|
| Dependencies | none (ships with every JDK) | Maven download | none, but Python not guaranteed |
| Java 22+ syntax (thingsboard, Java 25) | 5,494 / 5,494 files parsed | 11 files failed, 2 entry points lost | n/a |
| Constant-built paths (nacos) | resolved via AST | 433 / 433 correct | 170 / 433 wrong or unresolved (39%) |
| Speed, 5.5k files | 1.3 s parse (+3.4 s task setup, batchable) | 2.5 s parse | 6.9 s warm, 33 s cold |

The research report recommended JavaParser. The empirical spike showed two problems with it:

- JavaParser's support for new Java syntax trails each Java release, so it rejected Java 22+ code.
- It needs a Maven dependency download, which failed on this machine because the global
  `settings.xml` points to an unreachable corporate Nexus.

javac has neither problem, because it always parses the syntax of the JDK it runs on.

Rules for the real scanner:

- A file that fails to parse produces an `UNKNOWN` record and is re-scanned by a regex
  fallback. It is never dropped silently. The parse-failure count goes into the manifest.
- Set the parse release from the running JDK (`Runtime.version().feature()`), not a
  hard-coded number. The prototype hard-codes `--release 26`.
- Never resolve a constant by its bare simple name. Resolution is scoped by imports,
  package and enclosing types, and an ambiguous name yields `UNKNOWN`. The regex
  prototype's bare-name fallback produced 168 plausible-looking wrong paths on nacos.

What must be resolved, because each case was observed to matter on real code (empirical
report §3.3 and §4):

1. Class-level plus method-level path concatenation, including prefixes inherited from
   interfaces and superclasses, and nested controller classes.
2. Path, topic and cron constants: nested types (`Constants.Agent.ADMIN_PATH`), static
   imports, interface fields, `+` concatenation, cross-file references, lazy evaluation.
3. Attribute arrays (`path = {...}`, `topics = {...}`), producing one record per element.
4. Composed annotations defined in the repository, transitively, including the
   meta-annotation's defaults.
5. Mappings declared on interfaces or abstract classes, projected onto each implementation
   as `INFERRED`.
6. `@Schedules` containers, numeric constants and `timeUnit` enums in `@Scheduled`.
   Placeholders and SpEL are kept verbatim with `placeholder: true`: 30 of 33 thingsboard
   schedulers are `${...}`.
7. Generated sources. OpenAPI `interfaceOnly` controllers hid 36 of 37 petclinic-rest
   endpoints from both approaches. Scan `target/generated-sources` when it exists; otherwise
   emit `UNKNOWN` records and a manifest warning that a build is required.
8. Programmatic consumers. thingsboard is Kafka-based but has zero listener annotations.
   Detect consumer patterns (`KafkaConsumer`, `SqsAsyncClient.receiveMessage`,
   `MessageListenerContainer`, Spring Cloud Stream `Consumer<>` beans, Quartz jobs,
   `RouterFunction`) as `INFERRED` records.

Kotlin was absent from the corpus. If it appears, scan it with the regex path, mark every
record `INFERRED`, and warn in the coverage ledger.

### 2. Shipping: one small jar, invoked directly

```text
java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" <command> ...
```

- One jar contains both the scanner and the atlas query engine. Compile it with
  `--release 17`. It has no dependencies, so it stays small.
- No `.sh` or `.ps1` wrappers. On Windows, Claude may choose PowerShell over Git Bash, and
  `java -jar` behaves the same in both.
- No `bin/` directory, because claude.ai and Cowork refuse to install plugins that have one.
- `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` are substituted into skill Markdown.
  They are not exported to Bash commands, so pass any cache directory as an explicit argument.
- Rejected options: JBang (third-party download), `mvnw` on first use (blocked by corporate
  mirrors), JEP 458 source launch (requires JDK 22+), GraalVM native image (one build per
  OS, MSVC on Windows), Python and Node (not guaranteed to be installed).
- Undecided: whether the jar is committed or downloaded from a release into
  `${CLAUDE_PLUGIN_DATA}`. Because it is small and dependency-free, committing it is acceptable.

### 3. Atlas and query output: skills query projections, never load the atlas

Measured on thingsboard (1,063 entry points; tokens ≈ bytes / 4):

| View | ~Tokens |
|---|---|
| full JSONL | 102,000 |
| compact TSV (kind, file:line, Class.method, target, status) | 47,000 |
| minimal TSV | 25,000 |
| per-class summary | 3,000 |
| per-module summary | 120 |

Even the compact TSV is too large to load. The usable shape is a summary first, then filtered
queries. The Bash tool returns up to about 30,000 characters inline; anything longer arrives as a
file path plus a preview, and reading it costs another tool call.

Output contract for the query CLI (full proposal in the research report §4):

- The first line is a `#` summary: atlas commit vs `HEAD`, the match count, and a pagination hint.
- Lists are printed as TSV with a header and a default projection of about 40 tokens per row.
  Single records (`record`, `flow`) are printed as JSONL. `--format count` prints numbers only.
- The default is `--limit 50`, which is about 2k tokens. The worst-case default output stays
  under 20,000 characters.
- IDs are stable hashes (`EP-3f9a2c`), and ordering is deterministic. Byte-identical output
  keeps prompt caches valid and diffs clean.
- Zero matches exits 0 and suggests the closest matches. A non-zero exit is reserved for real
  errors and comes with a one-line fix. Failed commands are shown with only about 10k characters
  and no file path.
- Storage stays JSONL. Store `cls` as the fully qualified name and move FQN → file mapping into
  `types.jsonl`: repeated file paths take up 35–40% of every record.
- Incremental scans are correct only with a persisted index of types, constants, interface
  implementations and meta-annotations. Up to about 10k files, a full rescan (~0.6 ms per
  file) is simpler.

### 4. Skills: what costs tokens

- Skill descriptions are always in context and share a listing budget of 1% of the context
  window with every installed plugin, with a 1,536-character cap per skill. Keep descriptions
  under about 300 characters and put the trigger phrase first. Mark internal skills
  `user-invocable: false`.
- An invoked skill body stays in context for the rest of the session. Keep `SKILL.md` to the
  goal, the budget and the output contract. Put rule catalogues and schemas in `references/`.
- Flow tracing and audits run as `context: fork` with a dedicated agent, and only the finding
  packet returns to the parent.
- Use `` !`command` `` injection only for a short `stats` line, and always with `|| true`,
  because a failing command aborts the whole skill invocation.
- Run atlas queries through Bash or PowerShell with `allowed-tools` pre-approval, not through
  an MCP server. Idle cost is zero and accuracy is the same. Reconsider only if JVM start-up
  (~0.2–0.6 s per call) dominates eval durations.

### 5. Model and effort per skill family (to be confirmed by an effort sweep on fixtures)

| Family | Model | Effort |
|---|---|---|
| Mechanical classification, ledger, tickets | Haiku 5.5 | medium |
| Domain mapping, flow ranking | Sonnet 5.5 | medium |
| Flow tracing | Opus 5.5 (A/B Fable 5.1 `medium`) | high |
| Audit reasoning | Fable 5.1 (fallback Opus 5.5 `xhigh`) | high |
| Verification (fresh context, different model from the author) | Opus 5.5 | high |
| Dedupe | Sonnet 5.5 | low |

Fable 5.1 facts: 1M context, $10 / $50 per MTok, cache reads $0.25 per MTok, thinking
always on. Its prompting guidance says prompts that state goal and constraints beat
step-by-step prescriptions. Phrase rules as reliability concerns, not exploitation, to stay
clear of the cyber classifiers.

### 6. Accuracy of the LLM layer

- Evidence is `file:line` plus a verbatim snippet. A script re-reads the line at the pinned
  commit and rejects any snippet that does not match. This removes hallucinated evidence at no
  token cost.
- `mitigationsChecked` marks each mitigation listed in the rule as FOUND / NOT_FOUND /
  NOT_CHECKED. Any NOT_CHECKED caps confidence at MEDIUM.
- Verification tries to disprove the finding first, using an independent fresh-context agent
  limited to the evidence files plus three more. No self-consistency sampling: it multiplies
  cost and repeats the same blind spot.
- A golden fixture repository seeds one positive and one mitigated near-miss per rule. The
  truth file is hidden from the model. `claude plugin eval` graders: `tool_used: Skill`,
  `tool_used: Bash` on the jar (proves the atlas was queried instead of grepped), and `regex`
  over the findings file. CI tracks precision, recall and `costUsd` per rule.

## Untested assumptions, to check first

1. The order in which `${CLAUDE_PLUGIN_ROOT}` is substituted relative to `` !`command` ``
   execution in `SKILL.md` is not documented.
2. What happens when a skill sets `model: claude-fable-5-1` and the user's plan does not
   include it.
3. How the target monolith's SQS consumers are written: `@SqsListener`, or programmatic polling.
4. Whether the target uses OpenAPI-generated controllers, which would require a build before
   scanning.
5. JVM start-up cost per query call, measured in eval durations.
