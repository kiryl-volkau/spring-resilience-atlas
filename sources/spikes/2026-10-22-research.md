## 1. Claude Code mechanics that drive token cost

### Findings

**What is always in context vs loaded on invocation**

- Skills: "In a regular session, skill descriptions are loaded into context so Claude knows
  what's available, but full skill content only loads when invoked." Once invoked, "its content
  stays in context across turns, so every line is a recurring token cost."
  https://code.claude.com/docs/en/skills
- The listing has a budget: "The budget scales at 1% of the model's context window" (10K
  characters on a 1M-window model is roughly the order of magnitude; INFERRED arithmetic).
  Raise it with the `skillListingBudgetFraction` setting or the `SLASH_COMMAND_TOOL_CHAR_BUDGET`
  env var; `skillOverrides` can set a skill to `"name-only"`. Per skill, "the combined
  `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing"
  (configurable via `skillListingMaxDescChars`). https://code.claude.com/docs/en/skills
- After auto-compaction, invoked skill bodies are re-attached, "the first 5,000 tokens of each"
  with "a combined budget of 25,000 tokens". https://code.claude.com/docs/en/context-window
- Subagent descriptions: the parent sees agent descriptions in its Agent tool listing (this is how
  it picks an agent); the docs do not give a per-agent character cap. **INFERRED**: keep agent
  descriptions to one or two sentences for the same reason as skill descriptions.
- MCP tools: tool search is on by default, so "MCP tools are deferred and discovered on demand";
  only tool names and server instructions load at start. `ENABLE_TOOL_SEARCH=auto` loads them
  upfront "while their definitions total under 10% of the context window"; `false` loads all.
  https://code.claude.com/docs/en/mcp
- `/context` shows a live breakdown by category; the Skills row "reports the size of the listing
  after the budget is applied". `/skill-doctor` shows "what each of your skills costs and how often
  it gets used" (v2.1.252+). `/usage` attributes recent usage "to skills, subagents, plugins, and
  individual MCP servers" on paid plans. https://code.claude.com/docs/en/context-window,
  https://code.claude.com/docs/en/skills, https://code.claude.com/docs/en/costs

**Supporting files and progressive disclosure**

- "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." Example
  layout: `reference.md`, `examples.md` ("loaded when needed"), `scripts/helper.py` ("executed,
  not loaded"). Reference them from SKILL.md so Claude knows when to open them.
  https://code.claude.com/docs/en/skills
- A `CLAUDE.md` at the plugin root "isn't loaded as context"; put instructions in a skill.
  https://code.claude.com/docs/en/plugins-reference

**Frontmatter that matters for cost and isolation** (https://code.claude.com/docs/en/skills)

| Field | Effect |
|---|---|
| `disable-model-invocation: true` | Claude never auto-loads it; also blocks preloading into subagents |
| `user-invocable: false` | hidden from `/` menu, only Claude invokes it |
| `allowed-tools` | tools pre-approved "during the turn that invokes this skill" |
| `model`, `effort` | override for the invoking turn; effort `low`..`max` |
| `context: fork` + `agent` | runs the skill body as the prompt of a fresh subagent of that type; "The subagent doesn't see your conversation history"; `background` defaults to `true` |
| `shell: powershell` | runs `` !`command` `` blocks in PowerShell (requires the PowerShell tool) |
| `paths` | glob limiting automatic activation |
| `hooks` | registered on invocation; `once: true` is honoured only in skill frontmatter |

**Subagents** (https://code.claude.com/docs/en/sub-agents)

- Frontmatter: `model`, `effort`, `tools`, `disallowedTools`, `mcpServers`, `permissionMode`,
  `memory`, `background`, `isolation: worktree`, `skills`, `maxTurns`, `autoCompactWindow`,
  `omitClaudeMd`, `initialPrompt`.
- The parent "returns only the summary"; "Only the summary and a small metadata trailer come
  back". Transcripts are saved separately as `agent-{agentId}.jsonl`.
  https://code.claude.com/docs/en/context-window
- `skills:` preloads full skill content "at startup, up to the first 32 distinct names".

**Dynamic context injection `` !`command` ``** (https://code.claude.com/docs/en/skills)

- "runs shell commands before the skill content is sent to Claude. The command output replaces
  the placeholder, so Claude receives actual data, not the command itself." Substitution runs
  once; output is not re-scanned.
- Output over the Bash inline ceiling "arrives as a file path plus a short preview, not truncated
  text". Default 2-minute timeout per command.
- "A failed command aborts the entire skill invocation" (append `|| true`). Injected commands
  "never prompt for permission while the skill renders": a deny rule, or anything other than an
  allow result outside auto mode, aborts the invocation, so pre-approve with `allowed-tools`.
- Cost: the injected text becomes part of the skill message, which persists for the session and
  is re-attached after compaction (5K-token cap per skill). So an injected atlas summary is paid
  once per invocation but kept for the whole session.
- `${CLAUDE_PLUGIN_ROOT}` resolves "Anywhere in the Markdown body" of skill content
  (https://code.claude.com/docs/en/plugins-reference). **INFERRED**: the order of plugin-variable
  substitution versus `!` execution is not documented; test
  `` !`java -jar "${CLAUDE_PLUGIN_ROOT}/..." stats` `` once before relying on it.

**Bash tool output limits** (https://code.claude.com/docs/en/tools#output-limits)

- Valid result: "Inline up to roughly 30,000 characters by default; past that, the path of a file
  saved to the session directory and truncated past 64 MiB, plus a preview of up to the first
  2,000 characters, and Claude reads or searches the file when it needs the rest".
- Failure (non-zero exit, except exit 1 from `grep`, `rg`, `find`, `diff`, `test`, `git diff`,
  `git grep`): "Inline up to roughly 10,000 characters; past that, a head-and-tail excerpt ...
  with no file path".
- `BASH_MAX_OUTPUT_LENGTH` (30,000 default, ceiling 150,000) sizes the read-back window; the
  `bashOutputMaxChars` setting (v2.1.261+, up to 128,000) sizes inline ceiling and window
  together. `BASH_DEFAULT_TIMEOUT_MS` 2 min, `BASH_MAX_TIMEOUT_MS` 10 min.
- MCP: `MAX_MCP_OUTPUT_TOKENS` default 25,000 tokens; "Successful text results longer than 50,000
  characters are saved to a file regardless". https://code.claude.com/docs/en/mcp

**Plugin executables and data** (https://code.claude.com/docs/en/plugins-reference)

- `${CLAUDE_PLUGIN_ROOT}`: "Absolute path of the plugin's installed version"; changes on update,
  "so don't write state there". On Windows "the substituted paths use forward slashes".
- `${CLAUDE_PLUGIN_DATA}`: "`~/.claude/plugins/data/<id>/`, created on first reference and kept
  across plugin updates"; deleted on uninstall from the last place installed unless `--keep-data`.
- Neither variable is "present in the environment of commands Claude runs through the Bash tool";
  write the `${...}` reference in the Markdown body and Claude Code substitutes it inline. Hook
  commands and MCP stdio servers do receive them as env vars.
- `bin/`: "Files here are on the Bash tool's `PATH` while the plugin is enabled, so Claude runs
  them as bare commands. claude.ai and Cowork don't install a plugin that has this directory".
- SessionStart hooks: matchers `startup`, `resume`, `clear`, `compact`, `fork`; plain-text stdout
  or `additionalContext` is added to context; default command-hook timeout 600 s.
  https://code.claude.com/docs/en/hooks
- Windows shells: the Bash tool routes through Git Bash; the PowerShell tool is "enabled
  automatically" on Windows without Git Bash and on by default for claude.ai/Console accounts
  with Git Bash; "When the tool is enabled, Claude treats PowerShell as the primary shell."
  Hooks can set `"shell": "powershell"`. https://code.claude.com/docs/en/tools#powershell-tool
- How Anthropic's own plugins do it: `claude-security` declares
  `allowed-tools: Bash(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/render_report.py" *)` in SKILL.md
  and runs hooks as `sh "${CLAUDE_PLUGIN_ROOT}/hooks/hooks.sh"` with a `python3`/`python`/`py`
  probe; `code-modernization` ships TypeScript hooks and Python scripts. No official plugin ships
  a compiled binary or downloads one. (`gh api repos/anthropics/claude-plugins-official/...`,
  files `plugins/claude-security/hooks/hooks.sh`, `.../skills/claude-security/SKILL.md`.)

**`claude plugin eval`** (https://code.claude.com/docs/en/plugin-evals)

- Layout: `evals/<case>/prompt.md` (frontmatter `name`, `tags`, `runs` default 3, `max_turns`
  default 10, `timeout_seconds` 300, `model`, `allowed_tools`, `append_system_prompt`, `env`)
  plus `evals/<case>/graders/<name>.md` (`type`, `weight`, `arm`) and optional `case.yaml`
  (`schema_version: "1.1"`, `context.scaffold_script`, `context.history_file`, `context.add_dirs`).
- Six grader types: `regex`, `tool_used`, `tool_order`, `file_exists` (free, transcript/file
  based), `llm`, `baseline` (judge model). "There are no custom-code graders."
- Every case runs in "a fresh, isolated non-interactive session with only your plugin loaded";
  three runs per arm by default, plus a no-plugin baseline arm (`WITH`, `W/OUT`, `Δ`).
  "Runs never stop to ask for permission. Built-in tools that need a grant you didn't give, such
  as `Bash`, ... are removed", so grant `--allow-tools Bash` for scanner cases.
- Reported: per-case scores, `COST` ("a list-price estimate of the model calls"), JSON with
  `aggregates.overallScore`, `casesPassed`, `meanDelta`, `costUsd`, `durationSeconds`. Token and
  turn counts as fields: NOT FOUND IN DOCS.
- CI: `claude plugin eval . --trust-plugin --json results.json --threshold 0.8 --no-publish
  --max-cost-usd 20`; exit 0 pass, 1 below threshold, 2 partial (cost ceiling), 130/143 interrupted.
  Fixtures: "write a Bash script in the case directory and name it in `context.scaffold_script`"
  (runs only with `--scaffold`); `context.add_dirs` exposes fixture directories.

### Recommendation

1. Keep every skill description under ~300 characters with the trigger phrase first; the
   plugin will have 14+ skills and the whole listing shares a 1%-of-context budget with every
   other installed plugin. Mark internal skills (`finding-verifier-deduper`, `coverage-ledger`,
   rule catalogues) `user-invocable: false` or `disable-model-invocation: true` as appropriate.
2. SKILL.md bodies: goal, budget, output contract, and pointers to `references/*.md`; rule
   catalogues and schemas live in references and are opened only when a rule fires.
3. Deep audits run as `context: fork` skills with a dedicated agent (`agents/flow-auditor.md`)
   that has `tools: Read, Grep, Glob, Bash` and `omitClaudeMd` where the target's CLAUDE.md is
   irrelevant. The parent receives only the finding packet.
4. Use `` !`...` `` injection only for a short, bounded atlas summary (manifest + counts, under
   ~1,500 tokens) and always with `|| true`. Never inject record lists.
5. Scripts: design for the 30,000-character inline ceiling (see section 4) and exit 0 on "no
   results" so output is never classified as a failure (which hides the file path).
6. Do not use `bin/` (blocks claude.ai/Cowork installs; Bash-PATH only). Invoke executables by
   explicit `${CLAUDE_PLUGIN_ROOT}` path written in the skill body, passing `${CLAUDE_PLUGIN_DATA}`
   as an argument when a cache directory is needed.
7. Atlas queries: CLI through Bash, not an MCP server (see trade-off below).
8. Evals from day one: one `evals/` case per audit skill against a golden fixture repository,
   graded by `tool_used: Skill` + `tool_used: Bash` (scanner ran) + `regex` over the findings file
   the skill writes; CI gates on `--threshold` and archives `costUsd` as the cost series.

**CLI via Bash vs plugin MCP server for atlas queries**

| | CLI via Bash | Plugin MCP server |
|---|---|---|
| Idle context cost | zero | near zero (tool search defers schemas), but a JVM process per session |
| Output ceiling | 30K chars inline, then file path + preview | 25K tokens, file past 50K chars |
| Permissions | `allowed-tools: Bash(java -jar "${CLAUDE_PLUGIN_ROOT}/..." *)` pre-approval | MCP permission rules |
| Composability | Claude can pipe to `head`, `grep`, `wc` | fixed tool surface |
| Startup | JVM start per call (~0.3-0.6 s, **INFERRED**) | warm process, instant queries |
| Debuggability | run it yourself in a terminal; evals can `tool_used` it | protocol layer in between |
| Accuracy | identical: same data, same query engine | identical |

Recommendation: CLI for the MVP; revisit MCP only if per-call JVM start-up shows up in eval
durations. Accuracy is unaffected by the choice.

### Confidence

High for everything cited above; medium for the `!`-versus-`${CLAUDE_PLUGIN_ROOT}` ordering and the
JVM start-up estimate (both marked INFERRED).

## 2. Claude Fable 5.1 and the model/effort assignment

### Findings (source: bundled `claude-api` skill, SKILL.md model table cached 2026-10-06,
`shared/model-migration.md` § Migrating to Claude Fable 5.1, `shared/prompt-caching.md`,
`shared/cost-optimization.md` § 2.6-2.7)

| Model | ID | Context | Max output | Input / Output $/MTok | Cache read |
|---|---|---|---|---|---|
| Claude Fable 5.1 | `claude-fable-5-1` | 1M (default and maximum) | 128K | $10 / $50 | $0.25 (0.025x) |
| Claude Opus 5.5 | `claude-opus-5-5` | 1M | 128K | $4 / $20 | $0.20 (0.05x) |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | 1M | 128K | $2 / $10 | $0.20 |
| Claude Haiku 5.5 | `claude-haiku-5-5` | 1M | 128K | $0.10 / $0.50 (up to 100K-token prompts; $0.50 / $2.50 beyond) | ~0.1x |

Relative to Fable 5.1: Opus 5.5 is 2.5x cheaper, Sonnet 5.5 5x cheaper, Haiku 5.5 100x cheaper
per token.

- Thinking is always on; depth is controlled only by `output_config.effort`
  (`low`/`medium`/`high`/`xhigh`/`max`, default `high`). Forced `tool_choice` is rejected;
  thinking blocks are bound to the producing model. Same tokenizer as Opus 4.7/4.8.
- Effort guidance: "Lower effort settings - including `low` - still perform very well on Claude
  Fable 5.1, often exceeding the `xhigh` or even `max` performance of previous models." "At `low`,
  Claude Fable 5.1 is often competitive with Opus and Sonnet on cost per task while performing
  better - evaluate low Fable effort against below-frontier usage before reaching for a cheaper
  model." At `medium`, "results roughly match Claude Fable 5 at lower cost".
- Turn shape: "Individual requests on hard tasks can run many minutes at higher effort"; at
  higher effort on routine work it "can gather context and deliberate beyond what the task needs".
- Documented strengths relevant here: "long-horizon autonomous runs", "code review/debugging and
  repository-history search", "parallel sub-agent delegation and collaboration"; "Separate
  fresh-context verifier sub-agents tend to outperform self-critique." Caveat: "bug-finding gains
  exclude security-focused analysis, where the cyber classifiers apply" - reliability audits are
  not security audits, but phrase rules as reliability, not exploitation, to avoid classifier
  false positives (`stop_reason: refusal`, category `cyber`).
- Prompting: "Prompts and skills written for prior models are often too prescriptive for Claude
  Fable 5.1 and *reduce* output quality ... prefer stating the goal and constraints over
  enumerating the steps." "Give the reason, not just the request." Ground progress claims:
  "Before reporting progress, audit each claim against a tool result from this session."
- Prompt caching: prefix match; minimum cacheable prefix 512 tokens on Fable 5.1 / Opus 5.5 /
  Sonnet 5.5 / Haiku 5.5; writes 1.25x (5-min TTL); reads 0.025x on Fable 5.1. Claude Code manages
  breakpoints itself; the plugin's lever is prefix stability (stable skill text first, volatile
  atlas output after) and not switching top-level effort mid-session.
- Cost-optimisation guidance: "Sweep effort before touching the model"; "Price candidates in cost
  per completed task"; "Re-run failures at higher effort" when there is a checker; research-type
  work shows "nearly flat curves" across effort, long-horizon coding a real trade-off.
- In Claude Code, skill `model:` and agent `model:` accept aliases or full IDs
  (https://code.claude.com/docs/en/skills, https://code.claude.com/docs/en/sub-agents). Fable 5.1
  availability inside a given user's Claude Code depends on their plan; the plugin must degrade to
  Opus 5.5 when `claude-fable-5-1` is not available (**INFERRED**: the docs do not list an
  automatic fallback for an unavailable `model:` override; test what happens).

### Recommendation: model and effort per skill family

| Skill family | Skills | Model | Effort | Why |
|---|---|---|---|---|
| Mechanical classification | `entrypoint-catalog`, `side-effect-catalog` post-processing, `coverage-ledger`, `backlog-task-generator` | `claude-haiku-5-5` | `medium` | Checkable, schema-bound output over script data; 100x cheaper. Validate with a script (`validate-finding`), re-run failures on Sonnet. |
| Domain mapping | `domain-cartographer`, `critical-flow-discovery` (ranking) | `claude-sonnet-5-5` | `medium` | Needs judgment over package names, entities, queue names, but every decision is reviewable and recorded with confidence. |
| Flow tracing | `critical-flow-tracer` (forked agent) | `claude-opus-5-5` | `high` | Multi-file, dependent chain; the atlas keeps the read set small. A/B `claude-fable-5-1` at `medium`: the skill guidance says low/medium Fable often beats prior frontier at similar cost per task. |
| Audit reasoning | the seven `*-audit` skills (forked agent) | `claude-fable-5-1` | `high` | The accuracy-critical step; context is already narrowed to one flow and one rule, so the per-token premium buys reasoning, not reading. Fallback `claude-opus-5-5` at `xhigh` for teams without Fable. Do not use `xhigh`/`max` by default: "higher effort on routine work ... can deliberate beyond what the task needs". |
| Verification | `finding-verifier-deduper` (verify arm) | `claude-opus-5-5` | `high` | Fresh-context verifier, deliberately a different model than the author so errors are less correlated (**INFERRED** benefit; the documented fact is only that fresh-context verifiers beat self-critique). |
| Dedup / merge | `finding-verifier-deduper` (dedupe arm) | `claude-sonnet-5-5` | `low` | Mechanical: `dedupeKey`, same flow + same rule + overlapping evidence. |

Operational rules: set `effort` per skill in frontmatter, never change it mid-session; keep
the plugin's prompts goal-and-constraint shaped (de-prescribed) for Fable; run an effort sweep on

level names do not map to the same thinking across models.

### Confidence

High on model facts (bundled skill, dated cache 2026-10-06 - re-check pricing before release).
Medium on the assignment table: it follows the documented effort guidance but the actual
curve for this workload must come from the eval sweep.

## 3. Accuracy patterns for the LLM layer

### Findings

- Design report (`sources/deep-research-report(10).md` lines 368-423, 1641-1678): findings are
  evidence packets with separate `severity` and `confidence`; two-pass funnel (high-recall
  discovery, high-precision verification) with an "independent verifier" and dedupe step.
- Fable 5.1 guidance: fresh-context verifier sub-agents outperform self-critique; ground claims
  in tool results (`claude-api` skill, migration guide § Long-running agent recommendations).
- Plugin evals: graders are `regex`, `tool_used`, `tool_order`, `file_exists`, `llm`, `baseline`;
  "For long output such as a generated file, grade it with a `regex` grader over the file's
  contents"; "Give each case one grader on the result ... and one on the steps Claude took";
  fixtures via `context.scaffold_script` and `context.add_dirs`.
  https://code.claude.com/docs/en/plugin-evals
- Claude Code `tool-results` persistence and `agent-{id}.jsonl` transcripts allow post-hoc
  audit of what a skill actually read. https://code.claude.com/docs/en/context-window

### Recommendation

**Finding schema (schemas/finding.schema.json), fields that make or break accuracy**

```json
{
  "id": "F-2026-10-22-0007",
  "ruleId": "DUR-001",
  "commit": "a2bb857",
  "domain": "Billing",
  "flowId": "FLOW-billing-webhook",
  "severity": "CRITICAL",
  "confidence": "HIGH",
  "status": "CANDIDATE | VERIFIED | DISPROVED | DUPLICATE",
  "failureScenario": "…one concrete interleaving, naming the two instructions between which the process dies…",
  "evidence": [
    {"file": "src/main/java/.../BillingWebhookController.java", "line": 58,
     "symbol": "BillingWebhookController.handle",
     "snippet": "return ResponseEntity.ok().build();",
     "claim": "HTTP 200 returned before any durable write"}
  ],
  "mitigationsChecked": [
    {"name": "transactional outbox", "result": "NOT_FOUND", "where": "persistence.jsonl: no outbox entity in module billing"},
    {"name": "@TransactionalEventListener(AFTER_COMMIT) with durable event", "result": "NOT_FOUND"},
    {"name": "idempotency key on consumer", "result": "FOUND", "evidence": {"file": "...", "line": 112}}
  ],
  "sourceBudget": {"filesOpened": 5, "limit": 8, "expanded": false},
  "blastRadius": {"domains": ["Billing"], "effects": ["payment event lost"]},
  "recommendation": "...",
  "verification": ["Kill the process after 200 and before the executor runs; event must still be processed."],
  "dedupeKey": "DUR-001|FLOW-billing-webhook|BillingWebhookController.handle"
}
```

Rules behind the schema:

1. **Evidence is `file:line` plus the verbatim snippet.** A script (`validate-finding`) re-reads
   `file:line` at the pinned commit and rejects the finding if the snippet is not on that line
   (plus or minus 2 lines to absorb drift). This mechanically kills hallucinated evidence and
   costs no tokens. Findings with any unverifiable evidence are downgraded to `confidence: LOW`.
2. **Mitigation checklist per rule, recorded explicitly.** Each rule file in `references/rules/`
   lists the mitigations that would make the finding false (outbox, AFTER_COMMIT listener, SQS
   FIFO dedup id, idempotency table, retry with backoff, DLQ, lock, SELECT ... FOR UPDATE, ...).
   The skill must fill `mitigationsChecked` with `FOUND | NOT_FOUND | NOT_CHECKED` for every
   listed mitigation. Any `NOT_CHECKED` caps confidence at `MEDIUM`. This is the single most
   effective defence against false positives caused by mitigations the skill did not look for,
   because it turns "I did not see it" into "I looked here and it is not there".
3. **Separate severity from confidence** and never let the author skill set `VERIFIED`.
4. **Disprove-first verification.** The verifier agent gets only the finding packet, the rule
   file and atlas access, in a fresh context, with the instruction "find the mitigation or the
   reason this cannot happen; output `DISPROVED` with evidence, or `VERIFIED` with the one
   additional piece of evidence you confirmed". It is forbidden from re-tracing the flow from
   scratch (budget: the finding's evidence files plus 3). A different model from the author
   (section 2) reduces correlated mistakes (INFERRED).
5. **Independent verifier beats self-consistency here.** Self-consistency (N samples, majority)
   multiplies cost by N and the samples share the same blind spot (same prompt, same missing
   mitigation). One fresh-context verifier costs about 1x and attacks the blind spot directly.
   Use sampling only for the cheap classification steps if their eval shows instability.
6. **Source-reading budget is a field, not a wish.** `sourceBudget` is written into the packet;
   expansions require a stated reason from the rule file's expansion conditions.
7. **"No finding" is a coverage record**, written to `.reliability/coverage.jsonl` with flow,
   rule, commit, model, effort and files opened, never a safety claim.

**Golden fixture repository and precision/recall tracking**

- Build `fixtures/spring-golden/`: a small multi-module Spring Boot 3.x app with CRM / Billing /
  Resident / DailyCare packages, SQS listeners (via `@SqsListener`), `@Scheduled` jobs, `@Async`,
  `RestTemplate` and `WebClient` clients, Flyway. Seed each rule at least twice:
  one true positive (e.g. `BillingWebhookController` returns 200 then hands off to an in-memory
  executor) and one near-miss true negative where the mitigation exists (outbox table + relay).
  Record the ground truth in `fixtures/spring-golden/truth.jsonl` (`ruleId`, `flowId`,
  `symbol`, `expected: POSITIVE | NEGATIVE`). Keep the truth file out of `context.add_dirs` so the
  model never sees it.
- Each audit skill gets an eval case: `prompt.md` invokes the skill on one seeded flow; graders:
  `tool_used: Skill` (the skill fired), `tool_used: Bash` with `input_match` on the scanner jar
  (the atlas was queried, not grepped), `regex` over `.reliability/findings/<flow>.jsonl` for the
  expected `ruleId` + `symbol` (positive case) and a regex over the skill's summary line
  `RULES_FIRED: none` (negative case; negation via an explicit summary token because the grader
  set has no "must not match" documented - INFERRED).
- Precision/recall over time: a small script (`scripts/score-findings`) joins
  `findings/*.jsonl` with `truth.jsonl` per rule: precision = verified-true / all reported,
  recall = seeded positives found / seeded positives. Run it in CI after `claude plugin eval
  --json results.json --scaffold --allow-tools Bash`, append one row per run to
  `metrics/history.csv` (date, claude version, model, effort, precision, recall, `costUsd`,
  `durationSeconds`). Track per rule, not only overall; a rule whose precision drops below the
  threshold is the one whose mitigation checklist needs a new entry.
- Model drift: `claude plugin eval` pins `model` in `prompt.md`; re-run the suite when a model
  releases, compare `Δ` and the precision/recall rows.

### Confidence

High on schema and verifier design (follows the design report and the documented verifier
guidance). Medium on eval grader mechanics for negative cases (regex negation not verified).

## 4. Script output design for LLM consumption

### Findings

- Bash inline ceiling ~30,000 characters; beyond that Claude gets a file path and a 2,000-char
  preview and has to spend another tool call to read it. Failure output (non-zero exit, except
  listed search commands) is capped at ~10,000 chars with no file path.
  https://code.claude.com/docs/en/tools#output-limits
- Design report line 1619: Anthropic's context-efficient tool guidance "recommends
  filtering/pagination/range selection for large results".
- Fable 5.1 tokenizer is the Opus 4.7/4.8 tokenizer (claude-api skill); exact per-format token
  counts below are **INFERRED** estimates, to be confirmed with `count_tokens` on real output.

**Format comparison (INFERRED estimates on a 20-column entrypoint record)**

| Format | Tokens per record | Pros | Cons |
|---|---|---|---|
| JSONL, all fields | ~120-180 | self-describing, machine-parseable, `jq`-able | key names repeated every line |
| JSONL, projected (`--fields`) | ~40-70 | same, smaller | caller must know field names |
| TSV with one header line | ~25-45 | cheapest per row; `cut`/`grep` friendly; columns align | no nesting; tabs invisible if a value contains tabs (escape them) |
| Markdown table | ~35-60 | readable | pipes and padding waste tokens; useless for `grep` |
| YAML | ~60-100 | readable | indentation tokens, slow to parse |

### Recommendation

1. **Two output modes, one engine.** `--format tsv` (default for list subcommands, header line
   first) and `--format jsonl` (default for `record`, `neighbors`, and anything Claude will pass
   to `validate-finding`). `--format count` returns numbers only.
2. **Counts before rows.** Every list command prints a one-line summary first:
   `# 312 entrypoints match (domain=Billing kind=HTTP); showing 1-50 sorted by id; next: --offset 50`.
   Claude sees the size of the problem before deciding whether to page or narrow.
3. **Field projection** with `--fields id,kind,symbol,file,line` and a documented default
   projection per subcommand that fits ~40 tokens per row; `--fields all` for everything.
4. **Pagination** `--limit` (default 50, max 500) and `--offset`; the summary line always says
   whether more exist. Keep worst-case default output under ~20,000 characters so it never trips
   the 30K inline ceiling.
5. **Stable short IDs.** `EP-3f9a2c` = kind prefix + first 6 hex of SHA-1 over
   `(kind, module, fully-qualified symbol, annotation)`. Stable across scans while the symbol
   exists, independent of line numbers, short to quote in findings. Flows: `FLOW-<slug>`.
6. **Deterministic ordering**: sort by id, then file, then line; never by hash-map order. Same
   atlas, same query, same bytes, so prompt caches and diffs both work.
7. **Exit codes that steer**: 0 for success including zero rows (print `# 0 entrypoints match`
   and up to three suggestions: closest domain names by edit distance, the `domains` command,
   dropping a filter). Non-zero only for real errors (atlas missing, stale commit, bad flag), with
   a one-line message that names the fix: `atlas not found at .reliability/atlas; run
   /resilience-audit:repo-atlas-bootstrap`. Error text under 500 characters.
8. **Staleness is visible**: every command prints `# atlas @a2bb857 (HEAD a2bb857, clean)` or
   `# atlas @a2bb857 is behind HEAD 9c1d3e0 (14 files changed in 3 modules): run
   repo-atlas-bootstrap --changed`.
9. **No prose in stdout beyond `#` comment lines.** Claude can `grep -v '^#'` when it pipes.

**Proposed `query-atlas` CLI**

```
java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" <command> [options]

Global options
  --atlas <dir>        default .reliability/atlas
  --format tsv|jsonl|count   (tsv default for lists, jsonl for record/neighbors)
  --fields a,b,c|all   projection
  --limit N --offset N default 50 / 0
  --domain <name>      --module <name>   --status STATIC|RUNTIME_CONFIRMED|INFERRED|UNKNOWN
  --where key=value    repeatable exact-match filter on any field

Commands
  stats                               counts per record type, per domain, per module; manifest line
  domains [--min-confidence 0.6]      inferred domains with confidence and top packages
  entrypoints  [--kind HTTP|SQS|KAFKA|SCHEDULED|EVENT|WEBHOOK]
  transactions [--propagation ...] [--with-external-call] [--with-message-send]
  persistence  [--writes-only]
  producers | consumers [--broker SQS|KAFKA|RABBIT] [--queue <name>]
  async        [--kind ASYNC|EXECUTOR|FUTURE|APP_EVENT]
  clients      [--without-timeout] [--without-retry]
  migrations   [--since <version>]
  record <id>                          full JSON record for one id
  neighbors <id> [--depth 1..3]        call-graph neighbours of a symbol (callers, callees) from the static index
  flows [--domain X] [--rank]          ranked candidate flows (entrypoint -> tx -> side effects)
  flow <FLOW-id>                       the ordered hop list for one flow with ids for every hop
  changed --since <sha>                which atlas slices are stale for files changed since sha
  grep <regex> [--type ...]            regex over symbol/file/annotation fields of the atlas only
```

## 5. Shipping the deterministic scanner cross-platform

### Findings

- **JDK source launch.** JEP 330 (JDK 11) runs a single source file; JEP 458 (delivered in JDK 22)
  runs multi-file programs and "Programs that depend on libraries on the class path or the module
  path can also be launched from source files" (`java --class-path '*' Prog1.java`); classes are
  "compiled in memory" on every run, "if a compilation error occurs then the launcher will
  terminate after the program has already started executing". https://openjdk.org/jeps/458
  Spring Boot 3.x requires Java 17 or later (**INFERRED**, Spring Boot system requirements), so a
  JDK 22+ requirement for JEP 458 is not guaranteed on the user's machine; JDK 17/21 LTS are common.
- **JBang.** No JDK required: "If no `java` is found, JBang downloads one from Eclipse Temurin";
  zero-install launchers `curl -Ls https://sh.jbang.dev | bash -s - <args>` and PowerShell
  `iex "& { $(iwr -useb https://ps.jbang.dev) } <args>"`.
  https://www.jbang.dev/documentation/jbang/latest/installation.html
  Downside: a network download of a third-party launcher at first use, and `//DEPS` resolution
  needs Maven Central access.
- **Maven wrapper.** `mvnw`/`mvnw.cmd` download the Maven distribution "for the user first" from
  `distributionUrl` (Maven Central by default, `MVNW_REPOURL` for mirrors); "A POSIX-compatible
  Bourne shell is required to run the wrapper script" (the `.cmd` variant covers Windows).
  https://maven.apache.org/wrapper/ A build on first use also needs all plugin and dependency
  downloads (minutes, proxy-sensitive).
- **GraalVM native image.** Windows needs "Microsoft Visual C++ (MSVC) compiler version 14.x or
  later" (Visual Studio Build Tools), Linux gcc/glibc-devel/zlib, macOS Xcode; the builder
  produces a binary "for a specific operating system and architecture" and the page does not
  describe cross-compilation. https://www.graalvm.org/latest/reference-manual/native-image/
  So: three CI matrix builds, three downloads, and JavaParser reflection configuration (INFERRED).
- **Python / Node.** Not guaranteed on a Spring developer's machine (task statement); Anthropic's
  `claude-security` plugin needs a `python3`/`python`/`py` probe script precisely because of this
  (its `hooks.sh` tries all three). Python stdlib has no Java parser; regex-only discovery misses
  nested annotations, meta-annotations and multi-line signatures (INFERRED from scope).
- **Claude Code plugin mechanics.** `${CLAUDE_PLUGIN_ROOT}` is "Scripts, binaries, and config
  files bundled with the plugin"; `${CLAUDE_PLUGIN_DATA}` is for "Installed dependencies ...
  generated code, and caches"; `bin/` blocks claude.ai/Cowork installs; on Windows substituted
  paths use forward slashes; marketplace plugins are installed by cloning the repository, so
  every byte committed is downloaded by every user (INFERRED size concern).
  https://code.claude.com/docs/en/plugins-reference
- **Shells on Windows.** With the PowerShell tool enabled "Claude treats PowerShell as the primary
  shell. The Bash tool remains available for POSIX scripts when Git Bash is installed."
  https://code.claude.com/docs/en/tools#powershell-tool. A `.sh` wrapper therefore fails when
  Claude picks PowerShell; `java -jar ...` is identical in both shells.
- **How published plugins ship code.** Anthropic's official repository ships Python and
  TypeScript/Node scripts and `sh` hooks referenced via `"${CLAUDE_PLUGIN_ROOT}"`; MCP-based
  external plugins run `node server.ts` or `npx`; none ships a compiled binary or downloads one
  (`gh api repos/anthropics/claude-plugins-official/git/trees/main?recursive=1`).

### Options compared

| Option | Needs on user machine | First-use cost | Windows risk | Verdict |
|---|---|---|---|---|
| Fat jar committed in plugin, `java -jar` | JDK 17+ (guaranteed) | none | none; same command in PowerShell and Bash | **Recommended** |
| Fat jar downloaded from GitHub Releases into `${CLAUDE_PLUGIN_DATA}` | JDK 17+, network | one download, checksum check | TLS/proxy failures; needs a download script in sh and ps1 | fallback if repo size grows |
| Build with `mvnw` on first use | JDK 17+, Maven Central access | minutes, hundreds of MB | proxy/mirror config | no |
| JBang | network (downloads JBang and possibly a JDK) | seconds-minutes | fine, but a third-party installer | no for a corporate audience |
| JEP 458 source launch + dependency jar | JDK 22+ | recompiles each run | none | no (JDK 22 not guaranteed; parse errors surface mid-run) |
| GraalVM native image per OS | nothing | download per OS/arch | MSVC toolchain in CI, reflection config | later, only if JVM start-up matters |
| Python stdlib-only | Python (not guaranteed) | none | `py` vs `python` naming | no |
| Node | Node (not guaranteed) | none | fine | no |

### Recommendation

Ship a single prebuilt fat jar, built with `--release 17`, containing `javaparser-core` (no
transitive dependencies; INFERRED) and the query engine, at `scanner/dist/resilience-atlas.jar`,
committed on release tags by CI and `--plugin-dir`-usable in development after `mvnw package`.
Size budget under 5 MB. Invoke it directly, no wrapper scripts, so the same line works in Git
Bash, PowerShell, zsh and CI.

SKILL.md fragment (works on all three OSes):

```yaml
---
name: entrypoint-catalog
description: List the entry points (HTTP, SQS/Kafka/Rabbit consumers, schedulers, event listeners) of one business domain from the reliability atlas. Use when asked which endpoints, consumers or jobs a domain has.
argument-hint: "[domain]"
allowed-tools:
  - Bash(java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" *)
  - PowerShell(java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" *)
model: claude-haiku-5-5
effort: medium
---

Atlas status (injected at invocation):

!`java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" stats --format tsv || true`

Query the atlas, never grep the repository for what the atlas holds:

    java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" entrypoints --domain "$0" --limit 100

If the atlas is missing or behind HEAD, stop and tell the user to run
`/resilience-audit:repo-atlas-bootstrap` instead of scanning yourself.
```

Build-time invocation (`repo-atlas-bootstrap` skill):

```
java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" scan --repo . --out .reliability/atlas [--changed-since <sha>]
```

Notes: `--plugin-dir` development needs the jar present; add `mvnw package -q -DskipTests` to
the contributor README. If first-use download is ever adopted, keep the jar version and SHA-256
pinned in the plugin and cache under `${CLAUDE_PLUGIN_DATA}/scanner/<version>/`, passing that
path as an explicit argument because the variable is not exported to Bash commands.

### Confidence

High on platform facts (cited); high on the recommendation given the "JDK guaranteed, Python and
Node not" constraint; medium on the jar size and JavaParser dependency claims (INFERRED).

## Decisions for the plugin

1. Scanner and atlas query engine are one Java fat jar (`--release 17`, JavaParser) committed at
   `scanner/dist/resilience-atlas.jar`; invoked as `java -jar "${CLAUDE_PLUGIN_ROOT}/scanner/dist/resilience-atlas.jar" ...`
   with no shell wrappers and no `bin/` directory.
2. Atlas queries go through Bash/PowerShell with `allowed-tools` pre-approval, not a plugin MCP
   server; revisit only if JVM start-up dominates eval durations.
3. Atlas storage stays JSONL (diffable, pinned to commit SHA); the jar loads it per call. SQLite
   is deferred until a join-heavy query proves too slow.
4. `query-atlas` output contract: `#` summary line first with counts and pagination hint, TSV with
   header for lists (default projection about 40 tokens per row), JSONL for `record`/`flow`/
   `neighbors`, `--format count`, default `--limit 50`, output capped well under 30,000 chars,
   deterministic sort by stable hash IDs (`EP-`, `TX-`, `PR-`, `MQ-`, `AS-`, `XC-`, `FLOW-`), exit 0
   on zero rows with "closest match" suggestions, non-zero only for real errors with a one-line fix.
5. Skill descriptions under ~300 characters with the trigger first; internal skills
   `user-invocable: false`; rule catalogues and schemas in `references/`, loaded on demand;
   SKILL.md bodies state goal, budget, output contract and nothing procedural beyond that.
6. Flow tracing and every audit skill run as `context: fork` with a dedicated agent definition;
   the parent receives only the finding packet. Dynamic injection is limited to `stats` with
   `|| true`.
7. Model/effort: Haiku 5.5 `medium` for mechanical classification and ledger writing; Sonnet 5.5
   `medium` for domain mapping and flow ranking; Opus 5.5 `high` for flow tracing; Fable 5.1
   `high` (fallback Opus 5.5 `xhigh`) for audit reasoning; Opus 5.5 `high` for the fresh-context
   verifier; Sonnet 5.5 `low` for dedupe. Effort fixed per skill in frontmatter; confirmed by an
   effort sweep on the golden fixtures before release.
8. Finding schema adds `mitigationsChecked` (every rule-listed mitigation marked
   FOUND/NOT_FOUND/NOT_CHECKED), `sourceBudget`, `status`, and `file:line + verbatim snippet`
   evidence; `validate-finding` mechanically re-reads each snippet at the pinned commit; any
   unverifiable evidence or NOT_CHECKED mitigation caps confidence.
9. Verification is disprove-first by an independent fresh-context agent on a different model,
   budgeted to the finding's evidence files plus three; no self-consistency sampling for audits.
10. A golden fixture Spring Boot repository with seeded positives and mitigated near-misses per
    rule, truth file hidden from the model, drives `claude plugin eval` cases (graders:
    `tool_used: Skill`, `tool_used: Bash` on the jar, `regex` over the findings file); CI runs
    `claude plugin eval . --trust-plugin --scaffold --allow-tools Bash --json results.json
    --threshold 0.8 --max-cost-usd <n>`, appends precision/recall/cost per rule to a history file,
    and re-runs on every model release.
11. Prompts are written goal-and-constraints style (de-prescribed) for Fable 5.1, phrase rules as
    reliability (not exploitation) to stay clear of cyber classifiers, and include the
    "ground claims in tool results" instruction in every forked agent.
12. Coverage ledger entries record flow, rule, commit, model, effort and files opened for every
    run including "no finding"; the plugin never reports "safe".
